
# PM-2026-03 · Payments ran out of database connections after a config change

- Date: 2026-03-14
- Services: payments, api-gateway
- Severity: SEV-1
- Duration: 47 minutes

## Summary

During the nightly EMI auto-debit job, payments returned timeouts for most requests. A release that afternoon had lowered the database connection pool limit as part of a cost-saving change.

## Impact

About 1,900 auto-debit payments failed between 02:04 and 02:51. Customers saw "payment could not be processed" and the operations team re-ran the failed debits the next morning.

## Root cause

Release payments v1.9.4 reduced the database connection pool from 40 to 8. Daytime traffic never needs more than 8 connections, so testing passed. The auto-debit job opens about 30 connections at once, so the pool ran out and requests waited until they timed out ("Timed out waiting for a database connection").

## What fixed it

Rolling back to v1.9.3, which restored the pool size of 40. Errors stopped within one minute of the rollback.

## Lessons and follow-ups

- Any change to connection pool size must be load-tested with the auto-debit job's traffic, not daytime traffic.
- Added an alert when payments errors exceed 5 per minute between 02:00 and 03:00.
- Pool size changes now need a second reviewer from the database team.
